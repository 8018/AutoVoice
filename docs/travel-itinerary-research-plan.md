# 城市旅游攻略调研与项目实施方案

调研日期：2026年9月30日。范围以“北京有什么好玩的”“北京一日游攻略”“北京两日游攻略”为准，面向现有 AutoVoice 项目的语音入口。本文是实施建议，尚未实现或验证供应商接口；项目现状依据当前工作区代码，不代表线上部署状态。

推荐在现有业务语音链路上增加旅游攻略能力，采用“旅游内容检索、地图数据校验、行程编排、Markdown 流式下发、弹窗动态渲染与语音摘要”。本次不做“导航到第一站”或其他攻略到导航的联动，也不接导航 SDK；地图 API 仅用于景点查询和路线可行性校验。

核心交付要求：正文格式为 Markdown，生成过程中持续下发，Android 弹窗实时渲染；不得等待整篇生成完成才下发，也不得把完整结果切片播放当作模型流式输出。旅游任务先经过既有仲裁和 DM 接纳，正文与完成状态均属于该任务的更新，不再次参与同轮语义仲裁。

## 搜索工具与导航 SDK 的分工

| 能力 | 合适的数据或工具 | 本次需求是否需要 |
| --- | --- | --- |
| 城市有哪些值得玩的地方、适合什么人 | 旅游内容搜索或维护过的旅游知识库 | 需要内容依据；通用互联网搜索可由优质知识库替代 |
| 景点的准确身份、地址和位置 | 地图 POI 搜索及详情 API | 一日游、两日游路线需要 |
| 闭馆日、预约方式、临时公告、季节活动 | 官方旅游内容检索或合作方数据接口 | 输出这些事实时需要核验 |
| 景点如何按天组合、各玩多久 | 大模型加行程规则校验 | 需要 |
| 两站之间是否顺路、交通多久 | 地图路径规划 API | 承诺具体路线可行性和交通时间时需要 |
| 应用内实时导航、到达和偏航回调 | 导航 SDK 或车机导航接口 | 不属于第一版攻略需求 |

这里有两种不同的“搜索”：地图搜索负责找地点；内容搜索负责解释为什么值得去、怎么玩、有哪些限制。导航 SDK 主要解决实际出行引导，即使 SDK 套件附带 POI 查询，也不等于拥有完整旅游内容。

官方能力核对结果：

- 高德 POI 2.0 支持地点和详情查询，文档列有营业时间、部分类型的评分／人均消费、入口坐标等可选字段。具体字段可能缺失，不能把“人均消费”直接视为景区门票价格，也不能把常规营业时间当作节假日或临时开放承诺。[高德 POI 2.0](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)
- 高德路径规划 Web API 支持路线策略和有序途经点，可以在服务端校验行程，不要求手机先嵌入导航 SDK。它计算交通路线，不负责每天游玩时长、午饭和预约时段的组合。[高德路径规划 2.0](https://developer.amap.com/api/webservice/guide/api/newroute)
- 高德 MCP 已提供地点搜索、详情、路线、天气以及导出专属地图等能力。专属地图功能接收已经生成的行程，因此不能把它当作旅游内容或行程正确性的来源。实际项目能调用哪些能力，要以其 MCP 工具发现结果和账号权限为准。[高德 MCP 能力说明](https://lbs.amap.com/api/mcp-server/summary)
- 导航 SDK 的到达回调适用于后续行中服务，对本次城市攻略生成不是前置条件。[高德导航回调接口](https://a.amap.com/lbs/static/unzip/Android_Navi_Doc/com/amap/api/navi/AMapNaviListener.html)

因此，演示性的泛泛推荐可以只用大模型；可实际参考的一日游、两日游产品，应接入可靠内容源并做地图校验。无需每问一次都进行全网搜索，可优先使用有效缓存及维护过的城市资料。

## 第一版产品行为

| 用户输入 | 建议行为 |
| --- | --- |
| 北京有什么好玩的 | 按历史文化、胡同街区、自然风景、亲子等主题给少量代表选项，说明适合谁；不先追问一串条件 |
| 北京一日游攻略 | 直接给适合初次到访、节奏适中的草案，声明日期和出发点尚未指定；优先同一区域的景点组合 |
| 北京两日游攻略 | 分为两天，每天有主题、游玩顺序、预计停留、交通段和必要提醒；避免景点重复和跨城来回折返 |
| 带孩子，别太累 | 在当前行程上降低步行和景点密度，保留城市与天数 |
| 第二天换成室内 | 只修改第二天，保留第一天及用户已确认条件 |
| 明天去，故宫能安排吗 | 按具体日期核验开放及预约规则；未知余票必须明确未知，不能把预约入口存在当成有票 |

用户没有说日期时给通用草案，不猜“明天”，也不声称某天一定开放。有日期后再检查星期、节假日、预约条件与天气覆盖范围。用户未指定交通方式时，可以标注一个可修改的市内交通假设；车载语音入口不意味着景点之间都必须自驾。需要从酒店出发时才询问或使用酒店地址。“北京有什么好玩的”不依赖用户当前定位，也不能把手机所在城市替换为北京查询范围。

旅游请求进入处理后打开攻略弹窗，检索阶段显示明确的进度状态，首段正文就绪后立即开始渲染 Markdown。标题、段落、列表、强调、链接和表格随着内容到达更新，最终保留完整攻略。首页保留“查看攻略”入口。

播报采用独立的短摘要：先讲推荐主题、每天的大致安排和最关键提醒，再支持“详细说第一天”。建议初始播报控制在约20至30秒，作为产品目标实测调整。流式 Markdown 不直接送入 TTS，不逐 token 播报，不朗读来源网址或整篇攻略。

## 推荐的实现流程

1. 理解请求，提取目标城市、天数、日期、兴趣、同行人、强度、预算和交通偏好。只有缺失信息会阻止有效回答时才追问。
2. 检索城市主题和候选景点。优先官方景区、文旅部门、博物馆等可信来源；经验性内容用于推荐理由，开放和预约规则优先核验官方来源。
3. 把景点名称匹配到目标城市的 POI，保留供应商 POI ID、地址和坐标系。遇到同名景点或分馆不能直接取第一条。
4. 按区域和主题形成行程骨架，先流式输出已有依据的推荐概览，再逐日完善交通与时段。对选中的交通段调用地图算路，减少无意义的全量两两算路。
5. 由确定性规则检查当前待发布部分的每日时间、营业窗口、交通和步行负担；每个部分具备事实依据后，就让正文生成器以流式方式输出该部分。不得把“等全部行程和整篇正文完成”设为开始下发的前置条件。用户指定的必去点若不可行，应解释冲突并给选项，不能静默删除。
6. 最终校验后收口 Markdown 文档并保存结构化攻略，单独返回简短播报，允许继续修改。生成中的内容标记为草案；若后续核验需要修正已展示部分，用明确的文档快照替换，不能在末尾追加一份矛盾结论。本次不提供攻略导航操作。

每日总时间应包含“景点停留＋交通＋步行进出＋吃饭休息＋缓冲”。地图只提供其中的交通部分。停留时长和排队缓冲通常是规划估算，要明确标注，不能冒充实时数据。未来日期的路程耗时也不能称为当天实际路况预测。

内容事实建议保存 `sourceUrl`、`sourceTitle`、`fetchedAt`、`publishedAt`（可空）、`validForDate`（可空）与核验状态。模型的推荐理由和时长估算单独标记。网页内容只作为事实材料，不作为可执行指令。

## 工具与供应商选择

推荐保留现有高德接入，新增一个可替换的内容搜索适配器，不为攻略功能更换整个语音模型。

| 选项 | 调研依据 | 本项目建议 |
| --- | --- | --- |
| 独立联网搜索 API | 腾讯云 SearchPro 提供搜索接口和站点筛选，可返回含来源链接的结果；账号版本、配额和实际字段需联调确认。[官方接口](https://cloud.tencent.com/document/product/1806/121811) | 作为首个验证候选，通过 `TravelSearchProvider` 封装，便于现有 DeepSeek 与其他模型复用 |
| 模型平台内置联网搜索 | 百炼支持联网搜索、来源返回等配置，但取决于具体模型和接口。[百炼联网搜索](https://help.aliyun.com/zh/model-studio/web-search) | 作为备选适配；不能推断当前 Qwen 音频会话只加一个开关就自动拥有完整攻略能力 |
| 自建城市旅游知识库 | 本项目的工程选项，需要自行维护景点内容、日期和来源 | 后续对热门城市建设精选资料，降低重复搜索成本；第一版不必先引入向量数据库 |

高德 MCP 的现有工具若缺少所需详情字段、交通方式或稳定结构，就在地图适配层补充 Web API。MCP 是接入协议，实际能力取决于上游服务和工具 schema，不能认为“已有 MCP”就已经有完整攻略能力。

首轮验证应比较中文景点召回、官方来源覆盖、正文与来源返回、时效过滤、响应时间和实际计费。没有真实调用数据前，不声称某家效果最好或估算固定每次成本。费用主要由搜索次数、地图调用次数和模型输入输出量组成。

缓存建议按事实类型配置有效期：城市介绍可以较长，预约和活动规则更短；出行前的重要规则应重新核验。路线估算保存计算时间，供应商数据缓存与展示按相应授权执行。搜索失败时可提供注明未核验的通用草案，但不能继续输出确定的开放、票价或余票结论。

## 流式 Markdown 协议设计

沿用现有 WebSocket，新增 `document_stream` 消息类型。外层继续使用项目的 JSON 消息封装，正文 `markdown` 字段始终是 Markdown 原文，不是 HTML，不是行程 JSON，也不在 Markdown 外再套代码围栏。新客户端通过握手声明 `markdownStreamVersion=1`；旧客户端接收最终文字摘要，新客户端必须实际增量显示。

每条消息包含 `streamId`、`utteranceId`、`segmentId`、`planId`、`revision`、单调递增 `seq`、`op`、`format=text/markdown`。文字输入另回显已有 `requestId`。`streamId` 标识一次生成，`revision` 标识一次计划修改，`seq` 标识消息顺序，三者不可混用。

| op | 载荷 | 客户端行为 |
| --- | --- | --- |
| `start` | 文档标题、身份及版本 | 关联任务已经仲裁胜出且被 DM 接纳后，打开一次弹窗；start 本身不代表胜出 |
| `progress` | 检索／算路／整理等状态 | 更新弹窗状态栏，不混入攻略正文，不算首个正文 |
| `delta` | 新产生的 `markdown` 片段 | 按 seq 追加到原文缓冲，持续动态渲染 |
| `snapshot` | 当前累计完整 `markdown` | 原子替换原文，用于修正或传输队列合并，不是追加；客户端接受同一有效流的较新快照 |
| `complete` | 最终完整 `markdown`、结束序号、计划引用、可选 `speakText` 摘要 | 最终全文对账、标记完成；通过当前任务检查后播摘要一次；禁止在完成后继续追加 |
| `error` | 失败码、简短说明 | 保留已收到的草稿，明确标记未完成，允许用户重试 |

服务端对同一流通过单一有序发送队列分配 seq。WebSocket 同连接本身有序，seq 主要用于防止应用层重复、并发发送及重连残留混入。重复／旧 seq 丢弃；delta 出现缺口后停止拼接，等待同一有效流的 snapshot 或 complete 校准；超时则保持未完成状态。不能静默漏字后显示成功。

新客户端先通过一个有效旅游任务候选完成本轮语义仲裁；DM 采用后将任务保持在执行中，不能沿用“收到普通文字回复即结束”的处理方式。后续 complete 是该任务的完成事件，由 DM 校验任务身份后完成文档与语音收口，不再投递第二个普通语义 Reply。错误或取消同样只结束对应任务。旧客户端保留最终文字回复的兼容路径，两条路径按能力协商选择，不同时运行。

建议每50至100毫秒合并已有小片段下发，避免每个 token 一个消息；complete 前立即冲刷剩余数据。初始上限建议为每篇64 KiB UTF-8 正文，均为待实测调整的工程参数。积压时合并成较新的 snapshot，不丢弃孤立 delta 后假装连续，也不使用无限队列。超过上限应中断并标记未完成或明确缩短后重新生成，不能无提示截断。

第一版断线后保留已有草稿并显示“连接中断”，终止该流，不自动续写或补执行。重新生成使用新的 streamId；旧连接回调不能恢复旧流。在线路恢复后读取已完成计划、跨会话收藏属于后续能力。

## 仲裁与生成流程

旅游域识别产生有效的“生成攻略”任务候选，包含请求条件和任务身份；候选经过现有服务端与端侧仲裁，获胜后仍须由 DM 确认是否属于当前轮。不能把“正在处理”、首个 token 或 document_stream.start 当作仲裁胜出，也不增加 UI 自行决定的旁路预览许可。

DM 采用旅游任务后才打开弹窗并释放该任务的 Markdown 增量；生成完成、失败和摘要是该任务的状态更新，不逐片或再次参与仲裁。同轮仍只采用一个语义候选，任务开始不要求全文已经生成。本地先胜出时不显示攻略；旅游任务胜出后，同轮迟到本地结果不能替换它。新轮成立、取消或断线时，按既有身份校验和输出闸门拒绝旧内容。仲裁器不持有“当前轮”状态，DM 继续负责当前轮与任务生命周期。

流程分成资料获取、内部计划和正文生成：工具调用的碎片只用于内部装配，完整参数校验通过后才能执行工具；工具轮的临时文字不能直接当成攻略。正文阶段使用无动作工具权限的流式生成器，输入已经核验的事实和当前分段计划，输出纯 Markdown。已有依据的概览先输出，后续按天／章节继续输出，不等待最后一天或整篇文章完成。

内部 `TripPlan` 保留城市、天数、日期、偏好、每日有序景点、交通、来源、`stopId`、可信 `poiId` 和坐标系；Markdown 是其面向人的呈现。将正文与计划绑定到同一 revision，最终核对景点顺序及关键数字。生成失败或最终校验失败时保留草稿并标记未完成。本次不把 Markdown 中的地名、序号或链接解释为导航操作。

当前经典工具循环默认20秒、旧 Qwen 音频循环45秒，不等于整个流式文档的 SLA。[项目预算说明](./agent-execution-budget.md) 旅游文档应单独配置总截止时间、首正文超时和流空闲超时，并与客户端等待及网关超时一起校准；收到流片段可以更新空闲计时，但不能无限延长总截止时间。

### 新输入时取消旧攻略生成

取消作为节省资源的尽力操作，输出正确性始终由仲裁、DM 和任务身份检查保证。首版仅补齐当前攻略 LLM 请求的取消接线，不为此重构全部 ASR、候选计算、共享 MCP 会话或供应商取消接口。

代码依据：`DeepSeekLlmProvider.chat` 已在返回 Future 被取消时调用对应 OkHttp `Call.cancel()` 并中断 worker；`ExecutionBudget` 也有中断和截止时间处理。因此，为新建攻略生成任务保留直接请求句柄并调用取消，改动相对有限。但当前网关 `turn_commit`／`cancel_turn` 主要撤销输出许可，不会自动取消该 LLM；经 `thenCompose` 等包装后也不能假设取消会自动穿透。

触发顺序如下：

1. 新 VAD 开始时记录新 capture，不立即取消旧生成。只有声音可能是噪声或回声。
2. 该新 capture 有有效的非空识别文本，且 DM 接纳为新轮后，立即使旧任务输出失效，并对旧攻略的 LLM 句柄发起一次取消。可用被现有准入规则接受的增量识别，不要求等整句最终 ASR；单独的 VAD 或尚无有效文本的事件不触发这一取消。
3. 显式文字请求在 DM 接纳后同样取消旧生成，不要求制造 VAD；用户点击“停止生成”也直接走旧任务的取消入口。
4. 取消精确绑定 owner／session／turn／task／stream 身份，绝不能只取消某个可变的“当前 Call”，也不能误停新轮 ASR。相同任务多次取消幂等，先设置终止标记再取消句柄，覆盖取消与下一次请求启动的竞争。
5. 不等待取消返回才处理新输入。取消异常、不支持取消的工具或已经在途的片段均不阻塞新轮；让旧任务在既有预算内自然结束，DM 拒绝其所有迟到输出。

只保留停止信号和当前生成 Call 的轻量管理，不为搜索/MCP 增加远端撤销确认、取消重试或完成对账。已持有可直接取消的请求可以顺带释放；否则按原截止时间收口。关闭本地连接也不等于供应商保证即时停止计算或停止计费，不以此作为产品承诺。

## Markdown 弹窗与渲染设计

新增 `TravelGuideDialog`，通过 Compose `Dialog` 自定义宽高和内容，内部为状态栏、可滚动 Markdown 正文、停止生成／重试／关闭按钮。复杂内容的 Dialog 需要自行定义容器和布局。[Android Dialog 文档](https://developer.android.com/develop/ui/compose/components/dialog)

优先验证 `multiplatform-markdown-renderer` 的原生 Compose 实现，其当前文档提供异步解析和 StreamingMarkdown 状态接口；版本选择必须通过当前项目 Kotlin／Compose 编译与运行验证。[渲染库官方仓库](https://github.com/mikepenz/multiplatform-markdown-renderer) 如引入它需要大范围升级，第一版采用 `Markwon + AndroidView/TextView` 实现同一渲染接口，Markwon 可将 Markdown 渲染为 Android 原生文本。[Markwon 官方仓库](https://github.com/noties/Markwon) 两种方案最终只选一种交付，不同时维护两套。

共同要求：

- 第一版支持标题、段落、有序／无序列表、粗体、斜体、引用、分隔线、行内代码和链接；常用表格作为首版验收项，宽表可横向滚动。攻略提示词优先使用标题和列表。
- 网络片段不是完整 Markdown 节点。先按序追加原文，再解析文档；不能逐个 delta 单独渲染后拼 UI。未闭合强调、链接、表格或代码围栏按未完成文本容错显示，后续补齐再重排。
- 渲染在后台解析并约100毫秒合并更新一次，解析任务携带文本版本，旧解析结果不能覆盖新内容。UI 保持上次可用渲染，避免等待解析时清空闪烁；complete 后执行一次最终解析。
- 首版64 KiB上限内可以节流后重解析全文，先保证正确性和实测流畅；使用支持增量的库时再复用其尾部重解析。不能自行假设空行前内容永远稳定，因为后续 Markdown 可能改变前文解析。
- 原文与渲染结果分别保存，保持 Unicode 和换行完整。最终完整渲染必须与同一份 Markdown 一次性渲染一致。
- 用户在底部时跟随新增内容；用户向上阅读后保留阅读位置，显示“有新内容／回到底部”，不强行拉回。快照替换时尽量保持可见段落锚点。
- 关闭弹窗只隐藏，生成继续，首页可再次打开；同一流后续片段不会自动弹回。“停止生成”终止展示并尽力取消 LLM，保留未完成草稿。新的有效输入被 DM 接纳时也停止旧任务输出并尽力取消；新请求使用新流和版本。
- 转屏或配置重建使用 ViewModel 中的文档状态，不重启生成；退后台不主动拉起弹窗。进程被杀后恢复的草稿不标记为仍在生成。
- 来源使用可点击的普通 HTTPS 链接。原始 HTML、脚本、自动外链图片和任意导航 URI 不作为首版渲染能力；本次没有攻略导航入口。
- Markdown 内容不写入 `lastReplyText` 后再被最终摘要覆盖。文档内容、弹窗可见性、生成状态和语音摘要各自有明确字段；停止播放语音不等于取消正文生成。

## 验收用例与测量指标

| 验收项 | 通过条件 |
| --- | --- |
| 真正流式 | 可控上游先发送一段真实正文，再阻塞结束事件；客户端必须在解除阻塞前看到已渲染正文。真实模型也记录首次正文早于生成完成 |
| 端到端不缓冲 | 分别记录上游首正文、服务端首 delta、客户端接收和首帧渲染；不能只证明服务端收到分片 |
| 初始体验 | 旅游请求被路由并获展示许可后，目标1秒内弹窗出现；搜索状态不计为首正文。上游首正文到界面可见目标为 p95 小于500毫秒，需在指定真机和网络条件下实测 |
| 增量格式 | 刻意在中文、换行、`**`、链接、列表和表格内部切片；无乱码、崩溃、重复，最终与一次性渲染一致 |
| 排序与收口 | 重复 delta 不重复追加；缺口不静默遗漏；新 snapshot 能校准；complete 后旧 delta 不改变文档；完成事件不重复仲裁或打开弹窗 |
| 中断与失败 | 首段之前及之后分别断网、超时、取消、替换；保留对应草稿；只有 VAD／空识别不取消，有新轮有效识别后才取消；取消未生效也不影响新轮和旧输出拦截 |
| 弹窗阅读 | 生成中上滑不被拉回；关闭后不反复弹出；重开保留文本；转屏不重复请求；后台不抢前台 |
| 版本与仲裁 | 两轮修改交错到达时只更新当前计划；被本地命令否决的云端任务不显示；任务胜出后同轮迟到候选不能替换；所有攻略结果均不触发导航 |
| 内容质量 | 北京推荐与目标城市一致；一日／两日天数正确、交通与休息计入预算；开放预约有依据，无日期时是通用草案 |
| 播报 | Markdown 不逐片进入 TTS；最终摘要仅一次；打断播报不意外清空文档 |
| 长文性能 | 在约定测试设备上持续输入至正文上限，记录解析耗时、帧卡顿、队列峰值和内存；超过上限有明确终态 |

新增指标至少包含：从请求到首个有用正文的耗时、从模型增量到屏幕显示的耗时、完成耗时、停流次数、取消延迟、渲染耗时、正文长度、工具调用量和模型用量。所有时间目标都是设计验收目标，本次尚无实测结果。

本次仅更新调研与任务规划，没有实施功能代码、安装渲染库、运行付费接口或进行真机测试。
