# 端云仲裁消息流水线

## 结论

端侧和云端仲裁都采用进程级常驻的 Handler 式串行消息流水线。仲裁器本身没有
“一轮开始/结束”的生命周期，也不知道哪个 `turnId` 是状态机的当前轮。它只做两件事：

1. 按固定业务规则决定候选何时可进入就绪队列。
2. 串行处理就绪消息，并保证同一 `turnId` 只输出一个语义。

候选是否仍属于当前对话轮、当前状态是否还能采用结果，由下游会话状态机判断。

## 端侧流程

```text
云端语义 ─────────────┐
本地车窗语义 ──────────├─► FIFO 消息队列 ─► 同 turnId 单输出 ─► 会话状态校验
云端不可用时的本地语义 ───┘
本地普通语义 ─► 入队门外等待 cloud.waitMs ─┘
                         pending 只延后这个入队时间
```

重要语义：

- “等云端”的是本地普通语义，它在等待期间尚未入队；队列里不存在一个 50 秒后才能处理的消息。
- 云端语义到达后立即入队，不等本地链、不等 pending 定时器。
- 本地车窗语义在云端优先窗口内立即入队；超过窗口后按普通本地兜底记录原因。
- 已进入就绪队列的合格候选按到达顺序处理，先入队者胜出。
- 本地 `unknown` 只丢弃该条消息，不占用本轮输出名额，后到云端语义仍可胜出。
- 仲裁胜出不取消本地或云端候选；迟到候选由同轮单输出闸门拦截。

`CandidateCoordinator` 只启动候选生产者并立即返回，不等待仲裁结束，也不维护
LISTENING/UNDERSTANDING 等第二套状态。对话控制器的 THINKING/SEMANTIC_PROCESSING 和录音层
的聆听定时器各自收口所属资源，都不向仲裁器发“轮次过期”指令。

## 云端流程

云端使用同一种串行消息模型，但保留云端自己的业务规则，不复制端侧规则：

```text
离线空调命中 ─────────┐
LLM 回复 ─► 离线未决时暂存 ──├─► 串行消息队列 ─► 同 turnId 单输出
安全超时兜底 ─────────┘
```

- 离线空调命中立即胜出。
- LLM 结果在离线结果未决时最多等待 `offlineGraceMs`；离线未命中或宽限到期后放行。
- `safetyTimeoutMs` 是服务端资源和用户体验的有界兜底，不是仲裁器的会话生命周期。
- Future 回调和定时器只投递消息，真正的胜者选择只在单一串行处理器中发生。
- 端云仲裁消息队列都有固定容量；过载时向生产者/请求返回显式失败，不无界积压。
- 决策日志、过程事件等观察回调与胜者输出相互隔离；单个观察者异常不会卡死
  Handler 排空标志，也不会阻止本轮结果交付。

## 不变式与验收

1. 仲裁器不查询最新轮，不持有 `ConversationController` 或 `DialogueStateMachine` 引用。
2. 同一 `turnId` 最多有一个语义输出，不同 `turnId` 互不影响。
3. 双路都没有结果时不伪造 `both_failed`；状态定时器回收 UI/会话状态。
4. 有效云端语义不受本地等待窗口或 pending 影响，到达即可入队。
5. 完整回归包括端侧仲裁器、`CandidateCoordinator`/`VoiceEngine`、云端 `RaceArbiter` 以及全仓构建与 lint。
6. 观察回调抛异常时，当前胜者仍交付，后续轮仍可继续仲裁。
