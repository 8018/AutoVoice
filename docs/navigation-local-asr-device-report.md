# 本地 ASR 设备诊断（2026-11-13）

## 观察与原因

当前把命令词插件装入唤醒 SDK 的本地诊断 AAR 可以初始化唤醒，但本地命令词 ASR
报 `get ability parser failed`。设备日志还明确出现：

```text
auth request failed:2016,未发现能力(请检查 SDKID 与 能力ID 是否相对应)
```

这是 SDK 身份与请求能力不匹配的证据。仅包含两个 native 插件不等于包含两种能力的
授权协议。共享运行时的 READY 状态也不能代替逐能力的可用性验证。

## 已试修正及结果

初始化原先未显式传入能力列表。按官方 API 增加
`ability("e75f07b62;e867a88f2")`，并验证交付 SDK 确有该方法和 `getAbility()`。
参数回归测试先失败、修正后通过；该修正后的设备运行仍出现 2016 和缺失 parser，
因此第一轮配置实验**没有解决本地 ASR**，不得标记识别成功，也不作为可交付修复。
本次运行唤醒 READY 不能排除依赖旧授权缓存；清空缓存或全新安装后，两能力请求可能
同时受该 SDK 身份错误影响。实验参数变更不应随当前单能力 core 发布。

两个原始 AAR 的 Java API 相同，但 `libAIKIT.so` 不同。插件合并工具现拒绝不同 core，
并在失败时保留已有输出；相同 core 的打包结果也必须经授权和设备验证。

## 剩余阻塞与验收

需要讯飞提供同时包含 `e75f07b62` 和 `e867a88f2`、与应用授权匹配的 Android arm64
官方组合 SDK。未找到有文档支持的 `cfgFile` 协议覆盖方案；不能把二进制拼接或修改
授权协议当作受支持的修复。现有被忽略的旧 AAR 仅保留为诊断产物。

取得组合 SDK 后仍须在设备上完成：联网授权、两种能力初始化、真实唤醒和命令词识别、
唤醒后多轮与错误边界验证。真实识别测试尚未通过，本报告不宣称设备、语音或驾驶验收完成。
导航相关变更还须按 AGENTS.md 完成离线测试和部署到 dev 后的全量云端门禁；本次打包
工具测试不能替代这些门禁。

参考：[讯飞命令词 Android SDK 文档](https://www.xfyun.cn/doc/asr/AIkit_commandWord/Android-SDK.html)
