# AutoVoice 生产系统架构评估

评估日期：2026-09-11。代码基线：`main` / `a6951ec`。

## 1. 结论与评估边界

**当前架构适合继续演进为生产系统，但现阶段不宜认定为已经具备生产就绪条件。**
主要差距不是模块数量或类的大小，而是身份隔离、业务状态提交、任务终态、过载控制、
发布恢复和数据治理尚未形成可验证的闭环。建议保留模块化单体及端云双层架构，不整体重写，
也不以全面微服务化作为前置条件。

本次按“面向真实用户、持续运行、处理真实位置和语音、有外部工具调用”的手机语音助手评估。
若接入真实车辆控制，执行授权与车辆状态约束必须增加专门验收；手机导航通过验收不代表
真实车控通过验收。本报告不构成车辆功能安全认证或法律合规结论。

依据为仓库源码、CI/部署脚本及现有设计文档。本次未访问生产主机或审计生产密钥配置，未实施
渗透测试、容量压测、真机回归或灾备演练，也未重新运行全量测试。线上环境变量、网络隔离、
GitHub 环境审批、备份有效性等均不能由仓库单独证明。下文路径相对仓库根目录，符号名用于定位。

证据分为：

- **已确认**：源码或配置直接体现的行为。
- **风险推导**：由该行为推导出的异常场景，不能直接归因到历史故障。
- **待验证**：需要运行环境、设备或压力实验才能下结论。

### 1.1 生产就绪矩阵

| 维度 | 当前判断 | 主要依据 / 差距 |
| --- | --- | --- |
| 模块分层与可替换性 | 可沿用 | contracts、适配器、Agent Loop、导航领域、端侧协调器已分层 |
| 会话与仲裁职责 | 方向正确，提交边界仍需补齐 | 当前轮与逐轮仲裁已分离，但导航候选会提前写入共享状态 |
| 身份与权限隔离 | 上线阻断项 | 恢复会话未绑定设备所有权；生产鉴权缺失时可默认放行 |
| 外部动作安全 | 接入有副作用工具前必须补齐 | 工具调度策略不等于动作授权；候选计算期间即可调用工具 |
| 生命周期与故障隔离 | 不充分 | 关闭线程池不保证排队 Future 终结；原生调用超时不等于退出 |
| 流量与容量控制 | 有局部保护，未形成端到端边界 | 有队列和连接限制，但慢下行、排队预算、设备公平性有缺口 |
| 配置一致性 | 不充分 | 工具连接、schema、prompt 分别切换，在途请求没有版本租约 |
| 发布与恢复 | 有基础能力，缺少业务级证明 | 已有 SHA、备份和自动回滚，但健康检查主要是进程/端口 |
| 数据保护与可观测性 | 有基础设施，治理不足 | 语音落盘、共享访问令牌、诊断丢弃和容量缺少分级策略 |
| 测试可信度 | 单测基础较好，生产证据不足 | CI 有覆盖率门禁，但 Stub、变体装配、故障演练不等价 |

## 2. 必须保留的架构设计

1. 音频并发进入端侧和云端，云端离线与模型候选也并发；不能改成“离线未命中才给模型”。
2. 两级仲裁保持硬优先级：端侧车窗优先，否则等云端；云端空调离线优先，否则等模型。
   超时、宽限期和失败兜底是显式策略，不替换成首个结果获胜。
3. 仲裁器只按该轮 ID 判断是否已经输出语义，并按规则选出结果；它没有“当前轮”概念。
4. 会话状态机及输出准入层负责当前轮判断。旧轮结果可以完成仲裁，但不一定能用于当前交互。
   候选落败或被新轮替代不取消计算；自身超时、资源销毁属于独立生命周期事件。
5. VAD 只做采集/分段，不直接建立业务轮或停播，不重新引入 `SPEECH_CANDIDATE`。
   新轮由 ASR 话语成立或有效 NLU 触发；回声识别问题由识别链路治理。
6. ASR 先独立更新识别框；获准输出的语义带识别文本时再刷新。文本与音频均由原 TTS/播放边界承接。
7. 业务域走 ASR/LLM，显式闲聊走 Qwen Realtime，继续隔离闲聊 Skill 和 system prompt。
8. 导航候选归属逻辑会话，保留 TTL、候选标识和 `selectionId`；正常重连不等于新建导航业务会话。

此前重构解决了真实问题，不应推倒重来。但“已有关闭方法”“具备 TTL”“通过 CI”分别不等于
“所有在途任务必然结束”“不会被旧结果覆盖”“已经满足生产验收”。

## 3. 风险清单与改进要求

优先级说明：P0 是对外生产开放前的阻断项（注明适用条件）；P1 是可靠生产运行需要完成的事项；
P2 是根据容量、成本和维护数据逐步推进的优化。优先级不是已发生事故的严重程度评级。

### R1 · P0：设备鉴权不等于会话所有权校验

**已确认：** `VoiceGatewayHandler.onHello` 验证设备令牌后，直接根据客户端提交的 `sessionId`
调用 `SessionRegistry.get` 恢复上下文，没有比较会话所有者；Registry 也未保存设备所有权。
`application.yml` / `application-demo-full.yml` 的 gateway 鉴权默认值为 false。
`TelemetryAuthInterceptor` 在令牌为空时放行。音频和 TTS 请求已有合法 hello 前的上下文检查，
因此这里不是“所有音频均可绕过 hello”的结论。

**场景：** 合法设备 A 获得设备 B 的会话 ID 后，可以请求恢复该会话。随机 UUID 降低猜中概率，
但不能替代所有权验证；配置遗漏则可能让生产服务以 demo 鉴权模式启动。

**改进：** 引入认证主体与会话所有者绑定；恢复时同时验证设备/用户、会话有效期和恢复凭据。
连接内禁止切换认证主体。生产 profile 对缺失认证配置直接拒绝启动；设备身份支持吊销和轮换。
遥测采集身份与管理员查询身份分离，读写按设备/用户范围授权。

**验收：** A 不能恢复或读取 B 的会话；错误/过期恢复凭据被拒绝；轮换后旧凭据失效；
生产缺少必要鉴权配置时无法启动。需另外核验真实生产环境是否已经有外围防护。

### R2 · P1：导航候选在输出准入之前修改共享业务状态

**已确认：** `contracts/NavigationDialog.complete` 在模型 Future 完成时立即调用 `remember`；
`navigation-domain/NavigationDialogService.remember` 随即按 sessionId 写入候选。
这个提交点不携带输出许可证或会话版本，先于最终输出准入判断。

**风险推导：** A 搜机场较慢，B 搜车站的候选先显示；随后 A 完成，虽然其下行被拦截，仍可能
覆盖服务端候选。用户选择屏幕上的车站时，新客户端可能因 selectionId 不匹配而失败，兼容路径
则可能使用不符合当前界面的候选。不能据此断言已发生过某一次错误导航。

**改进：** 分开“构建候选结果”和“提交会话状态”。候选计算可继续；会话/输出协调层准入后，
按 sessionId、业务版本及 selectionId 条件提交。领域存储只校验版本，不把当前轮概念塞回仲裁器。
若要求严格对应用户已经看到的列表，再增加显示确认协议，而不是把 send 成功当作已经显示。

**验收：** 人工控制 A/B 完成顺序，旧结果绝不覆盖新列表；重连、过期、关闭弹窗、重复选择均有
明确结果；客户端与服务端选中同一个 candidateId。不能通过取消旧候选掩盖竞争条件。

### R3 · 条件性 P0：工具调用的副作用没有独立提交边界

**已确认：** `agent-loop/RequestToolExecutor` 在模型循环期间调用工具；`ToolExecutionPolicy`
区分并行/缓存等调度属性，不是按用户、设备或车辆状态授权。`McpSkillRegistry.callTool`
有业务/闲聊 scope 隔离，但调用边界本身没有完整的动作授权上下文。

**风险推导：** 若接入“修改车辆设置”“创建订单”等有副作用 MCP 工具，落败候选也可能已经
执行动作。只拦截最终语义无法撤回该动作。当前 LLM 返回给客户端的车控 action 不等同于服务端
已经实控车辆；不能将未来工具风险写成已确认的真实车控漏洞。

**改进：** 保留读取工具的推测执行、依赖并行与请求缓存。写入工具输出待执行计划，只有获准采用
的结果进入 Execution Gateway：校验主体权限、参数白名单、业务状态、必要确认和幂等键，再执行。
真实车控的车辆状态约束由可信执行端负责，不放进 prompt 充当安全控制。

**验收：** 落败/旧轮候选不产生写入；重复消息与断线重试不重复执行；无权限动作被拒绝并审计；
执行超时返回“结果待确认”并查询状态，不能盲目重试或声称 exactly-once。
若暂不实现，生产工具清单必须限制为经过核验的只读工具。

### R4 · P1：任务资源关闭与 Future 终态还未完全一致

**已确认：** `AgentExecutionRuntime.close` 对两个线程池调用 shutdownNow，未处理被移出队列的任务。
`DeepSeekLlmProvider.chat` 返回独立 CompletableFuture，而 close 关闭 worker，未统一终结排队请求。
Hybrid 的 ASR `whenComplete` 回调调用 sink/route 后再完成 out：若这些调用同步抛错，异常进入
未使用的回调 Future，out 可能未完成。Qwen/Hybrid 的 active 索引只使用非空 utteranceId，
没有 sessionId，且入口检查与任务登记/关闭并非一个原子过程。

**场景：** 发布时排队请求没有明确失败通知；下行失败抛进 ASR 回调后，一轮一直等待；不同设备
使用相同 utteranceId 时任务登记互相覆盖。正常路径单测很难覆盖这些边界。

**改进：** 建立复合 RequestKey（主体/会话/轮/请求），统一任务登记和终态管理。关闭按
“停止接入 → 有期限排空 → 终结剩余请求 → 关闭传输和线程池”执行。回调异常必须完成对外 Future；
提交、登记、取消和关闭竞争均有确定语义。内部取消只用于自身截止或资源销毁，不改变仲裁约定。

**验收：** 排队时关闭、登记时关闭、sink 抛错、同名跨设备轮次、重复关闭等用例中，所有请求均在
约定期限进入一次终态，任务登记清空，线程数回落，无跨会话取消。

### R5 · P1：原生引擎超时后实际执行可能仍被占用

**已确认：** `NativeOfflineCommandProvider` 使用单线程 executor 的默认无界队列，
`out.orTimeout` 终结返回 Future，但不保证 JNI 调用结束。`OfflineEnginePool` 随返回 Future
完成释放许可。因此“调用方已超时”与“引擎实际空闲”可能不一致。

**风险推导：** 一次 native 调用卡死后，后续请求每次超时又释放许可，任务与音频仍可继续排进
同一个不可用 worker。Java interrupt 本身不能证明厂商原生调用可被终止。

**改进：** 立即增加有界引擎队列、健康状态和熔断；并发许可按实际执行生命周期归还。
为不可恢复或可导致 JVM 崩溃的 native SDK 规划独立进程隔离与 watchdog，按供应商契约验证后落地。
引擎不可用时明确降级，不无限排队；这与“离线候选慢就取消模型”无关。

**验收：** 注入永久阻塞/崩溃，网关仍可服务，队列内存有上界，在线候选正常工作，隔离进程可恢复。

### R6 · P1：局部限流不能替代端到端背压与预算

**已确认：** 网关有连接数、单段音频和部分线程池队列限制，这是已有保护。
但 `GatewayDownlink` 在调用线程中同步 sendMessage，只以 session 锁保证串行，未建立应用级
发送字节/时间预算。连接在 hello 前即计入配额，当前 handler 未见 hello 截止时间。
`onTtsRequest` 未限制文本长度。Agent 循环预算在工作开始后建立，外层排队时间不都包含在内。

**风险推导：** 慢客户端占住模型/音频回调线程；未握手连接耗尽接入名额；长 TTS 或排队请求
在用户已等待很久后才获得完整执行预算。是否已经造成线上延迟需要指标证明。

**改进：** 设置握手截止时间、每主体并发/速率配额、音频速率与积压上限、TTS 字数上限；
下行采用按字节有界队列和发送期限，定义控制消息与音频顺序及溢出处理，不能随机丢音频片段。
请求在准入时记录绝对 deadline，各阶段借用剩余预算；到期是自身生命周期终止。
外部模型/MCP 按供应商与租户设置舱壁和成本配额，记录拒绝原因。

**验收：** 慢读、只建连接不 hello、长文本、突发音频及上游变慢时，内存/线程有上界；健康客户端
延迟符合容量目标；拒绝有明确协议事件，不把过载伪装成识别失败。

### R7 · P1：Skill/schema/prompt 热更新缺少请求级一致快照

**已确认：** `McpSkillRegistry.refresh` 分别替换 sessions、toolOwners、导航 facade 和两个 prompt，
随后关闭旧连接。单项连接失败可跳过该项；请求没有持有旧配置的版本租约。

**风险推导：** 一轮看到旧 schema，却在工具执行时找到新连接或找不到工具；刷新关闭正在调用的
旧 session。配置一次保存成功不代表所有能力作为同一版本生效。

**改进：** 将 scope、工具 schema、连接引用、prompt、导航配置组成不可变 RuntimeSnapshot。
校验并预热候选版本后原子发布；请求持有快照租约，旧连接在请求退出或达到退役期限后关闭。
失败更新保留已验证版本；记录发布人、版本、验证结果，支持配置回退。

**验收：** 执行中刷新不破坏旧请求；新请求完整使用新版本；无效工具配置不静默删掉正常能力；
遥测能定位模型、prompt 和工具版本。llm/chat scope 继续隔离。

### R8 · P0/P1：诊断平台与管理面需要正式的安全和数据策略

**已确认：** telemetry 使用同一配置令牌作为 API 访问边界；`TelemetryService` 保存原始音频，
有保留期和有界写入队列，但不是按磁盘字节的总量治理。队列拒绝时可丢弃诊断写入；查询和写入
的可靠性要求尚需区分。`AdminController` 的 cookie 是管理口令的确定性散列，12 小时是浏览器
maxAge，校验端没有相应的会话过期状态；源码未设置 Secure。`SqliteSkillStore` 保存工具 auth_value。
Android manifest 开启 cleartext traffic，构建中存在向 BuildConfig 注入厂商凭据的路径。

**场景：** 诊断上传凭据泄露可能同时影响查询边界；重放管理 cookie 不受服务端会话期限约束；
语音量突增写满磁盘；客户端内嵌的长期秘密不能按服务器密钥的保密模型管理。
这些是代码边界风险，不等于确认生产端口公网开放或已经发生泄露。

**改进：** 对外开放前落实 TLS、后台访问隔离、读写分权及服务端可撤销管理会话；配置明确的
cookie 安全属性、CSRF 防护及登录限流。工具密钥采用受控秘密存储/引用，不在日志和导出中传播；
厂商客户端凭据按其支持的包名/签名绑定或短期授权模式评估，不能凭空假设能代理全部本地 SDK。
语音默认采集范围、授权、脱敏、保留与删除策略需产品确认；设置磁盘配额、分页查询、清理告警。
动作审计和安全记录不能沿用“诊断拥塞可直接丢弃”的语义。

**验收：** 越权读写被拒绝；会话到期/注销可服务端验证；发布包不包含不应下发的服务端秘密；
磁盘接近满载时可控降级；采集拒绝和丢弃有指标；备份与删除策略能实际执行。

### R9 · P1：部署成功判断仍停留在进程层

**已确认：** `.github/workflows/deploy.yml` 的自动路径等待 main CI 成功并使用对应 SHA；
有 known_hosts 校验、production environment 和部署回滚脚本，这是已有基础。
手动路径不验证该 SHA 的 CI 成功；部署重新构建 JAR，而非直接提升已验证产物。
`deploy-release.sh` 的健康判据是 systemd active 加 TCP 端口，回滚主要恢复 JAR，不涵盖数据库
和配置版本。gateway service 模板没有指定低权限 User，并运行 demo-full profile。

**场景：** 进程监听成功但模型鉴权/工具装配不可用，仍报告部署成功；代码回退后不兼容新数据库；
部署账号或应用进程被利用时权限过大。GitHub 环境是否配置人工审批未在本次验证。

**改进：** 手动/自动统一校验 SHA 和质量门禁，提升不可变产物并核验摘要；保留受控紧急通道和审计。
分开 liveness、readiness 与低频合成业务探测，不让昂贵模型调用成为每次健康探针。
先停止接入并排空，再滚动/蓝绿切换（单机也可先做受控维护与恢复）；回滚记录代码、配置、
schema 兼容矩阵，数据库采用可向后兼容迁移和经过演练的恢复方案。服务使用最小权限账号和资源限制。

**验收：** 故意部署坏鉴权/坏配置能被判失败；回滚后验证业务可用；发布中的请求有明确终态；
产物可追溯到已通过检查的 SHA；备份恢复演练有真实结果，而非仅有备份文件。

### R10 · P1/P2：单节点会话恢复和容量目标尚未形成产品契约

**已确认：** SessionRegistry、导航候选与部分聊天状态保存在进程内；网关结果去重缓存也在本地。
仓库部署以单主机服务和本地数据路径为主。这不等于技术上不能启动多个实例，也不是 SQLite
本身禁止扩容，而是尚无跨实例所有权、恢复和去重协议的完整证明。

**场景：** 进程重启或请求切到另一实例，界面还显示候选但服务端不认识；同一动作的重试未命中
原实例缓存。单纯增加负载均衡或把一张表放进 Redis 不能解决所有这些问题。

**改进：** 先定义重启时哪些状态允许丢、哪些必须恢复，以及 RTO/RPO。短期可以明确单实例能力
边界、重连后状态失效提示和重新同步；需要跨实例恢复时再引入共享状态存储、版本控制、会话
ownership/fencing 和动作账本。不能把过期音频重新播放当作恢复。

**验收：** 重启和换实例后无跨用户串会话、无重复动作；候选可恢复或明确要求重搜；演练测出
实际恢复时间和数据损失范围。是否必须双实例，由已批准的可用性目标决定。

### R11 · P1：测试和观测尚不能支撑生产承诺

**已确认：** CI 已覆盖 schema fixture、两种服务端变体、Android 单测/lint/构建、两个 Web 的
测试/构建和覆盖率。服务端聚合行覆盖率门槛为 75%；Android 模块门槛不同。
Omni 测试命令排除了 `:app:test`；Android 使用 `useIflytekStub=true`。它们不能证明 Omni
应用装配、真实 SDK、音频焦点和后台恢复全部有效。历史覆盖率见 `docs/test-coverage.md`，
本报告不把历史产物当成本次新测结果。

**改进：** 保留现有 CI，增加小规模真实装配集成测试、协议兼容测试、故障注入、真机周期测试和
长稳压测。观测区分“ASR 首字/终字、语义接受、首音频、开始播放、动作确认”，记录各阶段排队时间，
以及队列深度、拒绝、连接恢复、配置版本、上游错误和费用。日志相关 ID 不作为无限基数指标标签。

**验收：** 能定位“网络慢、ASR 慢、排队慢、模型慢、工具慢、下行慢、客户端播放慢”；
对慢客户端、上游断网、native 卡死、发布排空、热更新、旧轮晚到均有自动化场景。
真机覆盖导航切后台返回、播报中唤醒、多轮选择、蓝牙/音频焦点变化和长时间闲聊。
生产承诺使用实际端到端 p95/p99 与失败率，不能由覆盖率百分比推算。

## 4. 推荐的目标职责与状态所有权

| 边界 | 应负责 | 不应负责 |
| --- | --- | --- |
| 采集/ASR 适配器 | 音频、VAD 分段、识别事件、厂商资源生命周期 | 决定当前业务轮、决定停止播报 |
| ConversationController / 输出协调 | 当前轮、状态机、结果准入与界面/播放协调 | 重新实现识别算法、替代逐轮仲裁 |
| 两级仲裁器 | 每轮候选策略、该轮一次语义输出 | 维护当前轮、按新轮取消旧计算 |
| 导航领域 | 候选、匹配、TTL、版本条件提交 | 在所有模型完成回调中无条件覆盖状态 |
| Agent Runtime | 预算、工具依赖调度、读取缓存、任务终态 | 把模型输出直接当作写权限 |
| Execution Gateway（新增边界） | 动作授权、幂等、业务状态校验、确认与审计 | ASR/NLU 或模型推理 |
| 配置运行时 | 版本快照、校验、原子发布、旧连接退役 | 让在途请求跨多个不一致版本 |
| 接入与运维 | 主体绑定、配额、背压、排空、可观测性 | 改写产品仲裁规则以掩盖资源问题 |

这些是职责边界，不要求每一项新建服务。优先在现有模块内形成可测试接口；原生 SDK 故障隔离
可能需要独立进程，其他模块是否拆服务应由实际规模和部署需求决定。

## 5. 分阶段实施与发布门槛

每阶段拆为小 PR：明确行为变化、补回归、通过 CI、进行对应验收再合并。涉及部署、数据迁移、
权限或密钥调整时独立安排，不把本次评估当作执行这些操作的授权。

| 阶段 | 工作与依赖 | 完成标准 |
| --- | --- | --- |
| 0：确定生产边界 | 盘点部署入口、设备规模、读写工具、数据采集和供应商限制；确认 SLO/RTO/RPO | 有可验收目标和真实环境核对记录；不凭猜测宣布已安全 |
| 1：封闭信任边界 | R1、R8 的对外访问项；暂时只开放已验证只读工具 | 会话越权测试通过，生产配置 fail-closed，读写权限隔离 |
| 2：建立业务提交与执行边界 | R2、R3；先导航状态提交，再扩展到副作用工具 | 晚到不覆盖、落败不写入、重复不执行，且保留原仲裁规则 |
| 3：收敛生命周期与过载 | R4、R5、R6；先统一 RequestKey/终态，再队列/引擎隔离 | 故障注入下请求终态、线程与内存均有界；健康请求不被异常设备拖垮 |
| 4：配置与发布可恢复 | R7、R9；补配置快照和业务探测后完善回滚 | 在途热更新通过，坏发布能恢复，产物及配置版本可追溯 |
| 5：生产验收与容量扩展 | R10、R11、R8 数据治理；按 SLO 决定是否跨实例 | 真机/长稳/恢复演练通过，有容量报告和告警处置手册 |

R11 的测试与指标必须随每阶段建设，不是最后统一补课。R8 的访问控制先做，长期数据治理
继续推进。P0 未关闭前不扩展为公开生产服务；写工具执行边界未通过前不开放真实有副作用工具。

容量验收需要先填写：注册设备数、峰值连接数、同时说话比例、音频长度分布、闲聊持续时长、
允许的首字/首音频/动作延迟、每设备费用预算。现有默认连接数不是已压测容量。负载测试应覆盖
目标稳态、超额突发和上游退化，并记录测试机型、供应商配额与费用，避免无意义地承诺固定 QPS。
