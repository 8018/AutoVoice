## D14:数据保留、磁盘配额、秘密引用与审计分级(R8)

### 现状

| 项 | 现状 | 位置 |
| --- | --- | --- |
| 原始音频 | **默认采集并落盘**(`audio-dir`,`{utteranceId}.wav`);单文件上限 1.92MB | `TelemetryController`、`TelemetryService` |
| 保留期 | 默认 7 天(`retentionDays`),超期联动删除 rounds/events/音频 | `TelemetryService.cleanExpired` |
| 访问控制 | 上传/查询令牌已分离(D03a);管理登录已改服务端会话(D03b) | `TelemetryAuthInterceptor`、`AdminSessionStore` |
| 磁盘总量 | **无总量配额/水位监测**(只有单文件上限 + 保留期) | —— |
| 查询分页 | 列表接口**无分页**(见 `rounds` 查询) | `TelemetryController` |
| 工具凭据 | `SqliteSkillStore` 明文保存 `auth_value`(MCP 凭据) | `skill-manager` |
| 审计分级 | 诊断事件与安全审计**未分级**(队列满时可整体丢弃) | `TelemetryService` |

### 需要决策

**Q1. 生产是否持久化原始音频?**(计划文档建议:默认不持久化)
- 选项 A(建议):生产默认关闭音频落盘(`AUTOVOICE_TELEMETRY_AUDIO_ENABLED=false`),需要时按环境显式开启;开发/demo 保持开启。
- 选项 B:保持默认开启,但加磁盘总量配额与水位告警。
- 影响:A 合规风险最低、磁盘占用可控,代价是线上问题复现时缺少音频证据;B 保留诊断能力但需配额管理。

**Q2. 保留期与备份范围?**
- 当前 7 天。是否需要按"诊断数据 7 天 / 安全审计 90 天"分级?
- 备份是否包含音频目录?(服务器上没有独立备份方案,当前仅 SQLite 与 jar 备份)

**Q3. MCP 工具凭据的存储方式?**
- 选项 A(建议):保持明文但收敛文件权限(0600)+ 导出/日志脱敏,并在文档声明;后续再评估加密存储。
- 选项 B:引入密钥引用(环境中转)或加密存储,需要运维保管密钥。
- 影响:真实写工具开放前(A 仍属可接受),但若接入第三方生产凭据,建议 B。

**Q4. 审计事件是否独立可靠存储?**
- 现状:诊断事件队列满时整体丢弃(含动作安全事件)。
- 影响:动作审计若与诊断同级丢弃,事后无法追责;D07 的动作账本已在独立 SQLite,
  可作为审计基础,但需要"审计写入失败时拒绝相关写动作"的策略确认。

## D15:重启/重连的业务状态恢复协议(R10)

### 现状

| 状态 | 存放位置 | 重启后 |
| --- | --- | --- |
| 会话上下文(含 owner/resumeToken) | 服务端内存 `SessionRegistry` | **丢失**;客户端带 sessionId+token 重连 → `SESSION_EXPIRED` → 客户端清上下文全新握手(D02b 已实现) |
| 导航候选(逻辑会话 + TTL 120s + selectionId) | 服务端内存 `InMemoryNavigationSelectionStore` | **丢失**;客户端若仍显示列表,选择时会得到"地点列表已更新或失效,请重新搜索" |
| 动作账本(服务端签发) | 独立 SQLite | **保留**(持久化) |
| 手机动作本地账本 | Android SQLite | **保留** |
| 网关结果去重缓存(completedTurns) | 内存 | 丢失;同轮重发会重新走一遍(无重复副作用,因 actionId 幂等) |
| Realtime 闲聊会话 | 服务端内存 | 丢失;客户端需重连(已有重连逻辑) |

### 需要决策

**Q5. 停机容忍度与 RTO/RPO?**(决定是否需要跨实例/持久化会话)
- 选项 A(建议,单实例):接受"重启后客户端重连即新建会话";RTO≈进程启动时间(实测约 12s),
  RPO=0(动作账本已持久化,重复副作用被 actionId 幂等挡住);导航列表要求用户重新搜索。
- 选项 B:会话与导航候选持久化(Redis 或 SQLite),重启后恢复候选列表;RTO 不变但体验更好,
  需要额外存储与 ownership/fencing 设计。
- 选项 C:多实例 + 共享状态(计划文档明确:没有多实例演练前不承诺)。

**Q6. 客户端恢复行为是否需要加强?**
- 现状:收到 `SESSION_EXPIRED` / `SESSION_RECOVER_DENIED` 时客户端清本地上下文重连(已实现);
  但**导航列表在服务端丢失时,客户端界面仍显示旧候选**直到用户选择才发现失效。
- 选项 A(建议):客户端在重连(全新握手)时主动清空导航列表并提示"请重新搜索";
  需要客户端改动 + 一次真机验收。
- 选项 B:服务端在 ready 中返回"会话是否为新建立",客户端据此清列表(协议小改)。
- 影响:A 改动最小;B 语义更明确但加协议字段。

**Q7. 是否需要"重放到新实例"的能力?**(原计划 R10)
- 计划文档立场:若 SLO 要求换实例继续会话,另开共享状态/ownership/fencing 工作包。
- 需要你确认:**是否有跨实例继续会话的业务需求?**
