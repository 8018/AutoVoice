# dev 云端导航文本实测

直接向已部署的 dev 网关发送文本，检查真实回复和结构化动作，不通过手机执行。首轮 16 个场景、23 次文本请求，另对 4 个异常各复测一次，总计 27 次。测试时间以原始记录的 UTC 时间为准：2026-11-13T02:56:12.360Z。

## 结果

首轮 23 次全部收到回复：15 次符合步骤目标，4 次正确返回能力边界，4 次未达成用户目标。四项异常复测结果一致。不能把“收到回复”或“安全拒绝”计为对应导航功能完成。

耗时采用客户端单调时钟，从发送文本到收到最终 reply，包括网络、模型和地图搜索；不含连接握手、语音识别、语音播报、地图界面或设备动作。序号选择、取消等确定性回复只有约 30–40 毫秒，不能用总体平均数代表每次大模型推理耗时。仅单轮小样本，无并发和压力测试，P95 不代表生产服务等级。

## 覆盖范围与复跑

多轮场景按协议通知服务端当前候选已在客户端展示，再发送后续文本。每个场景使用独立会话，避免前一个场景残留影响下一个。候选、城市、否定、取消、换批和只读模式均检查了结构化动作，并非只看回复文案。

只读场景验证到 `preview_routes` 指令，未在本次测试继续调用路线预览接口，因此 0.033 秒是选点解析耗时，不是高德路线规划耗时。常用地址和活动导航状态需要真实设备上下文，本轮只验证缺能力时的反馈。原来的 208 条真机语料仍为未运行，没有用这些文本结果覆盖它们。

运行 `node tools/qa/navigation-cloud-text.mjs` 可重跑；`--focus=entrance,numeric_city,brand,charging` 单独复测四项。脚本读取本机忽略入库的认证配置，不输出令牌。每次运行会覆盖对应结果 JSON，并将评审置为待审核。
